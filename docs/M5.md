# M5 - Generalization Ladder

Date: 2026-08-18

Status: complete for the requested return-family ladder and one exchange-family holdout. M3 remains quota-blocked and was not resumed. No Bedrock calls, no tau2 agent runs, no general router, and no multi-category engine were built.

## 1. Technical Summary

M5 passes through the tested ladder:

| Family | Source task | Holdout task(s) | Highest rung passed | Meaning |
| --- | --- | --- | --- | --- |
| Return | `5` | `13`, `48` | Rung 3 | The return procedure generalizes with hand-fed inputs, and input discovery also works for both held-out tasks using local read tools only. |
| Exchange | `6` | `8` | Rung 4.3 | The exchange procedure is not return-specific; hand-fed and self-resolved exchange both pass for the selected held-out task. |

The rung-2-vs-rung-3 boundary is the key result: in these tested cases, the deterministic script did more than replay a hand-fed write procedure. It also resolved the write parameters itself from structured task-level requests using Retail read tools. That means the first observed boundary is not "procedure generalizes but input discovery fails." The actual boundary is narrower: this works for structured request objects and selected sibling tasks, but it does not yet prove free-form natural-language parsing, broad category routing, or robustness across the full task family.

All verifier checks used `EvaluationType.ENV`, tau2's programmatic DB end-state verifier. This avoids LLM judging entirely. Every script run reported `model_calls: 0`, `script_tokens: 0`, and `script_cost_usd: 0.0`.

## 5. What Rung 2 Proves

Rung 2 proves procedure generalization with hand-fed parameters.

For return, the task `5` procedure generalized to task `13` and task `48` once the target task's `order_id`, `item_ids`, and `payment_method_id` were supplied directly from the task definition.

For exchange, the task `6` procedure generalized to task `8` once the target task's `order_id`, old item ID, new item ID, and payment method were supplied directly from the task definition.

This confirms that the deterministic tool procedure is portable across task instances when the instance-specific constants are already known.

## 6. What Rung 3 Proves

Rung 3 proves input resolution for the selected cases, not just procedure replay.

Return task `13`:

- Input provided: customer email, return everything except keyboard and mouse, use a valid original refund method.
- Read tools used: `find_user_id_by_email`, `get_user_details`, and `get_order_details`.
- Derived write args: order `#W5490111`, item IDs `4579334072`, `6117189161`, `4947717507`, payment method `credit_card_3124723`.
- DB verifier result: pass.

Return task `48`:

- Input provided: customer name/zip, return the air purifier, refund on original method.
- Read tools used: `find_user_id_by_name_zip`, `get_user_details`, and `get_order_details`.
- Derived write args: order `#W9502127`, item ID `9534205511`, payment method `paypal_2433177`.
- DB verifier result: pass.

Exchange task `8`:

- Input provided: customer name/zip, inspect water bottle and desk lamp, after confirmation exchange only the desk lamp to a brighter one, preferring battery, then USB, then AC.
- Read tools used: `find_user_id_by_name_zip`, `get_user_details`, `get_order_details`, and `get_product_details`.

- DB verifier result: pass.

Plainly: in these selected tasks, the script can resolve inputs itself without an agent. The current break point is not at the hand-fed/self-resolved line. The untested break point is whether this still holds with raw natural-language request parsing and broader, messier task variation.

## 7. Honesty Checks

Did any rung make model calls?

No. All rungs made `0` model calls. The scripts do not instantiate the stock agent or user simulator, do not call Bedrock, and do not call tau2's LLM generation path. Rung 3 and rung 4.3 did not need quota.

Did the scripts genuinely execute workflows, or hardcode final DB state?

They genuinely executed Retail tool calls through `environment.get_response(...)` and then asked tau2's verifier to replay the resulting message trajectory. They did not mutate the DB object directly, patch final order fields, set DB hashes, or spoof reward outputs.

How were parameters obtained?

- Rung 1: task `5` values were parameters fed from the M4 trace.
- Rung 2: held-out task values were hand-fed from `evaluation_criteria.actions`.
- Rung 3: write parameters were derived from structured task-level request objects plus read-tool outputs.
- Rung 4.2: exchange task `8` values were hand-fed from `evaluation_criteria.actions`.
- Rung 4.3: exchange task `8` write parameters were derived from a structured task-level request object plus read-tool outputs.

What is still hardcoded?

The ladder scripts hardcode the selected source/holdout test cases and the structured request fields. They do not discover categories, choose tasks, parse arbitrary natural language, or route across procedures.

## 8. Where Generalization Breaks

No break was observed through the tested rungs:

| Family | Highest tested rung | Result |
| --- | --- | --- |
| Return | Rung 3 | pass on both held-out targets |
| Exchange | Rung 4.3 | pass on held-out target `8` |

The practical boundary exposed by M5 is subtler:

- Procedure generalization works with hand-fed write inputs.
- Input discovery also works for selected, structured request objects.
- The next unknown is free-form request interpretation and broader family coverage, not the deterministic execution or verifier path.

Important caveat: exchange rung 4 used task `8`, which is a close sibling of source task `6`: same customer, same order, same old item, different desired replacement. That is a clean one-variable test, but it is not the strongest possible cross-customer exchange generalization. Task `58` remains the natural harder exchange target because it changes user, order, product set, number of exchanged items, and payment method.

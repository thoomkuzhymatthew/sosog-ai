Date: 2026-08-18

Status: complete. M3 remains quota-blocked and was not resumed. This milestone made Haiku parser calls only; it made no Sonnet calls, no tau2 agent runs, no user-simulator runs, no router, and no multi-category engine.

## 3. Method

The Haiku prompt asked for one JSON object:

```json
{
  "status": "PARSED or AMBIGUOUS/INSUFFICIENT",
  "lookup": {"method": "email or name_zip", "values": {}},
  "return_item_names": ["Canonical Product Name"] or null,
  "keep_item_names": ["Canonical Product Name"] or null,
  "payment_rule": "original_payment_method" or null
}
```

The prompt included the 50 canonical Retail product names, but no order IDs, user IDs, item IDs, payment method IDs, task IDs, or DB state. Temperature was `0`, `max_tokens` was `512`, and prompt caching was not used.

The deterministic executor was the M5 return rung-3 path. It used local read tools to resolve customer, orders, items, and original payment method, then called `return_delivered_order_items(...)`. Verification used tau2 `EvaluationType.ENV`, the programmatic DB verifier.

Classification:

- Clean pass: Haiku parsed a usable intent, deterministic execution ran, and the DB verifier passed.
- Correctly deferred: the request was deliberately ambiguous or insufficient and Haiku returned `AMBIGUOUS/INSUFFICIENT`.
- Parse failure: Haiku produced the wrong usable intent, or failed to produce a usable intent for an intended-parsed case.

I classify functionally, not by string-identical JSON. For example, if Haiku emitted both an explicit return list and an equivalent keep list, and the deterministic script still produced the verifier-passing write, that is counted as a clean pass but recorded as a contract warning.

## 4. Headline Results

| Outcome | Count | Meaning |
| --- | ---: | --- |
| Clean pass | 10 | Cheap parse plus deterministic execution completed the ticket end to end. |
| Correctly deferred | 6 | Haiku recognized insufficient/conflicting language and avoided a write. |
| Parse failure | 2 | Haiku produced a wrong parsed intent; both caused wrong writes. |

Among the 12 requests intended to be parseable, Haiku handled 10 and failed 2. Among the 6 deliberately ambiguous requests, Haiku deferred 6 and guessed 0.

The core result: cheap parsing appears viable for clean-ish messy returns, and Haiku's deferral behavior is strong on obvious ambiguity. The unsafe boundary is specific but serious: schema-overfilled outputs and product synonym collisions can turn into wrong writes if passed directly to the deterministic executor.

## 6. Safety Failures

Two parse failures led to wrong writes:

| Case | Failure mode | Wrong write produced | Why it matters |
| --- | --- | --- | --- |
| `48_b` | Haiku output both `return_item_names=["Air Purifier"]` and `keep_item_names=["Vacuum Cleaner","Patio Umbrella"]`. | `return_delivered_order_items(order_id="#W9502127", item_ids=["9534205511","3877338112"], payment_method_id="paypal_2433177")` | The request said refund the purifier, not the vacuum. The overfilled schema caused the current deterministic script to also return the dumbbell set because it was not in the keep list. A strict schema gate would catch the both-list violation, but I did not build one in M5.5. |
| `73_a` | Haiku mapped "coffee machine" to `Coffee Maker` instead of the DB-relevant `Espresso Machine`. | `return_delivered_order_items(order_id="#W5272531", item_ids=["3320557165","2698416822","8098621301","7228247242","7441167885"], payment_method_id="credit_card_6824399")` | The customer intended to keep the coffee machine; the verifier target keeps the `Espresso Machine`. The parser returned the espresso machine too. This is the product-alias boundary: the cheap layer needs DB/context-aware disambiguation or must defer. |

These are confident wrong writes, not harmless no-ops. That means "Haiku parser + deterministic execution" is promising, but unsafe without a validation/defer layer around schema violations and synonym collisions.

## 7. Failure Map

What Haiku handled well:

- Direct customer identity by email or name/ZIP.
- Common aliases when they were unambiguous in the catalog: `bike` -> `Bicycle`, `camera` -> `Digital Camera`, `bottle` -> `Water Bottle`.
- Wrong order hints, because the downstream read resolver ignored order guesses and selected by customer plus item name.
- "Return everything except X" when X mapped cleanly to exact catalog names.

What Haiku safely deferred:

- Missing customer lookup.
- Missing product identity.
- Conflicting "maybe exchange, maybe return" requests.
- Vague categories such as "electronics item" or "one thing for coffee" without customer/order context.

Where Haiku failed unsafely:

- It sometimes populated both return and keep lists even though the prompt forbade it. This was benign in `13_b` and `73_b`, but harmful in `48_b`.
- It treated "coffee machine" as `Coffee Maker`, while the target task's expected kept item was `Espresso Machine`. This is not just a language issue; it is a catalog/context issue.

## 9. What Broke Or Surprised Me

The good surprise: Haiku deferred all six deliberately ambiguous cases. The ratio of parse failures to correct deferrals was 2:6, which is directionally good for a tiered architecture.

The bad surprise: both parse failures were confident enough to execute writes. The current deterministic return script does not question a parsed object once it receives one. That is fine for M5/M5.5 measurement, but unsafe as a product boundary.

The most informative break point is not "can Haiku parse anything useful?" It can. The break point is "can the cheap layer know when product aliases and over-specified schemas are unsafe?" Right now, not reliably enough.

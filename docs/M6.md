## 3. Gate Method

The gate has two deterministic stages.

Schema gate:

- Accepts only `status == "PARSED"` or defers on `AMBIGUOUS/INSUFFICIENT`.
- Requires a valid lookup: email, or first name + last name + ZIP.
- Requires exactly one item-selector list: `return_item_names` xor `keep_item_names`.
- Rejects parses where both lists are populated.
- Rejects unknown canonical product names.
- Allows `payment_rule == null` because this return-family executor only supports the original-payment path and already defaulted that way in M5.5. Unsupported non-original payment rules defer.

Catalog/consistency gate:

- Resolves the customer with read-only Retail tools.
- Reads the customer's orders before any write.
- For `return_item_names`, every requested product must resolve to exactly one item in exactly one delivered order.
- For `keep_item_names`, at least one kept product must anchor exactly one delivered order, no present kept product may duplicate inside that order, and the resulting return set must be non-empty. This avoids over-deferring task `13_a`, where the customer's broad "keyboard and mouse" wording includes a mouse outside the delivered order being returned.
- If resolution finds zero or multiple candidate orders/items, the gate defers.

Only if both stages pass does the harness call the unchanged M5 `run_self_resolved(...)` executor. Deferred cases do not enter the executor and therefore cannot write.

## 5. The Two M5.5 Failures

Both prior danger cases became safe deferrals.

| Case | M5.5 failure | M6 gate result | Write executed? |
| --- | --- | --- | --- |
| `48_b` | Haiku populated both `return_item_names=["Air Purifier"]` and `keep_item_names=["Vacuum Cleaner","Patio Umbrella"]`; the M5.5 executor returned an extra item and failed DB match. | Schema gate rejected the contract violation. | no |
| `73_a` | Haiku mapped "coffee machine" to `Coffee Maker`; the M5.5 executor returned the `Espresso Machine` and failed DB match. | Catalog gate found no `Coffee Maker` item in the delivered order, so it deferred instead of guessing. | no |

This is the central M6 result: wrong writes went from `2` to `0`.

## 6. Over-Deferral Cost

Two of the ten M5.5 clean passes were over-deferred:

| Case | Why M5.5 passed | Why M6 deferred |
| --- | --- | --- |
| `13_b` | The executor prioritized `return_item_names` and returned the right items. | Haiku also populated `keep_item_names`, violating the parser contract. |
| `73_b` | The executor prioritized `return_item_names` and returned the right items. | Haiku also populated `keep_item_names`, violating the parser contract. |

This is the safety/value tradeoff. The strict schema gate is good at catching `48_b`, but it also rejects two equivalent-but-overfilled parses that happened to execute correctly. The clean-pass survival rate is therefore `8/10` rather than `10/10`.

## 8. Honesty Checks

Did the gate make any model calls?

No. M6 made `0` new model calls. The gate itself made `0` model calls. It replayed 18 saved M5.5 Haiku outputs from `sosog-ai/metrics/m5_5_nl_boundary_results.json`.

Was a write executed on any deferred case?

No. `no_write_on_deferred` is `true` in the measured M6 result artifact. Deferred cases did read-only gate checks at most; they did not call `return_delivered_order_items(...)`.

Did M6 change the parser or executor?

No. M6 added `sosog-ai/crystallized/m6_validation_gate.py`. It did not edit `sosog-ai/crystallized/m5_5_nl_boundary.py` or `sosog-ai/crystallized/m5_return_ladder.py`.

Did the clean-pass cases genuinely execute the workflow?

Yes. Allowed cases called the unchanged M5 return executor, which executed Retail tool calls and then passed tau2's `EvaluationType.ENV` DB verifier.

## 9. What Broke Or Surprised Me

The schema gate carried most of the safety burden. It caught `48_b`, the clearest wrong-write bug, but it also caused both over-deferrals. That is useful evidence: the next design question is whether an equivalence-normalizer can safely convert "both lists populated but equivalent" into one canonical item selector, without reopening the wrong-write risk.

The catalog gate did exactly the thing M5.5 needed for `73_a`: it refused to infer that "coffee machine" meant `Espresso Machine` after the parser emitted `Coffee Maker`. That is the product-alias boundary. The gate should keep deferring there unless a future resolver has stronger catalog context.

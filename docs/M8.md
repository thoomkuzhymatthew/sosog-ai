# M8 - Automation Probe

Date: 2026-08-18

Status: complete. M3 remains quota-blocked and was not resumed. M8 used zero model calls. The target family was `cancel`, which was not previously hand-built; the prior hand-built families were `return` and `exchange`.

## 1. Technical Summary

M8 supports the middle interpretation: SOSOG looks like an automated core with human safety-review per family, not yet a fully self-scaling engine.

The executor was fully derived from traces. The schema gate and consistency-safety gate were generated from trace dataflow, tool docs, and observed pre-write state, but I cannot honestly mark them "fully derived" because the selector boundary and safety invariant required human review. The generated cancel environment passed all held-out ladder tests and deferred all adversarial cases with zero wrong writes.

| Component | Classification | Evidence |
| --- | --- | --- |
| Executor | Fully derived | Training traces aligned to one write skeleton: `cancel_pending_order(order_id, reason)`. |
| Schema gate | Derived + human-reviewed | Lookup/reason fields came from trace dataflow and tool docs; `target_item_names` as the self-resolution selector was generated from product anchors and human-reviewed. |
| Consistency-safety gate | Derived + human-reviewed | Ownership, `pending` status, and exactly-one-candidate checks came from the write tool name/docs plus observed pre-write trace state; human reviewed this as the family safety boundary. |

Interpretation: this is not "fully automated platform" evidence yet. It is evidence for roughly 80% automation with a human safety-review step per new family.

## 2. Recipe First

The generation recipe was written before applying it to cancel-family traces:

```text
sosog-ai/docs/M8_recipe.md
```

The recipe defines a family-agnostic flow:

1. Align passing traces.
2. Derive a parameterized executor from write skeletons and dataflow.
3. Derive the schema gate from tool signatures/docs plus trace structure.
4. Derive the consistency/safety gate from pre-write read results, write preconditions, ownership, candidate uniqueness, and verifier expectations.
5. Run a held-out generalization ladder and adversarial safety checks.

## 7. What Was Derived Vs. Reviewed

Executor: fully derived.

The write skeleton was unambiguous. Training traces for tasks `66` and `88` both ended in exactly one write call: `cancel_pending_order`. The write arguments were `order_id` and `reason`, both visible in aligned passing traces. The generated executor simply resolves customer/order data, applies the generated gate, and calls that tool with bound arguments. I did not write a separate cancel-family executor by hand.

Schema gate: derived plus human-reviewed.

The required lookup fields came from observed lookup tools. The `reason` enum came from the write tool docs and aligned training values. The need for exactly one selector, either `order_id` or `target_item_names`, came from the generated executor's need to bind `order_id`. This could be generated mechanically, but the choice that product names are the supported self-resolution selector is a boundary I human-reviewed.

Consistency-safety gate: derived plus human-reviewed.

The generated checks are ownership, pending state, and exactly-one candidate. The `pending` requirement came from the tool name `cancel_pending_order`, the tool docs, and the fact that every training target order had status `pending` before the write. Ownership came from the resolved user's order list and each order's `user_id`. Exactly-one candidate is the generic safety rule from the recipe. Still, I would not call this fully derived: confirming that this is the right cancellation safety boundary is a human safety-review step.

## 8. Product Interpretation

The evidence does not support "SOSOG fully automates new task environments" yet. The safety gate did not require hand-authoring, but it did require human review.

The evidence supports: executor derivation is automatable, and gate drafts are automatable, but production use needs a family-level safety-review step. That puts SOSOG closer to a product with a services or safety-review component than a pure platform today.

This is a good result, but it is not the maximal result. It says the core construction scales better than consulting, while the safety proof still needs a human in the loop.

## 1. Technical Summary

M4 proves the core SOSOG mechanic on one Retail task: a captured stable-pass trace can be turned by hand into a deterministic Python script, run without any LLM calls, and pass tau2's built-in programmatic Retail DB verifier.

Target chosen: task `5`.

Why task `5`:

- It is `3/3` stable-pass-looking in the M3 partial full-run checkpoint.
- It was also `10/10` pass in the M3 dry run.
- Its passing write skeleton is a single write call: `return_delivered_order_items`.
- The task is easy to audit because the script only returns one known item from one delivered order.

## 6. Honesty Checks

Did the script make any model calls?

No. It does not instantiate the stock agent or user simulator, does not call Bedrock, and does not call tau2's LLM generation path. It runs local Retail tools and `EvaluationType.ENV` only. The script reports `model_calls: 0`, `script_tokens: 0`, and `script_cost_usd: 0.0`.

Did it pass by genuinely executing the workflow, or by shortcutting/hardcoding final DB state?

It genuinely executes the captured workflow tool sequence. The only DB mutation is the real Retail tool call `return_delivered_order_items(order_id="#W6390527", item_ids=["8538875209"], payment_method_id="paypal_7644869")`. It does not directly set order status, `return_items`, DB hashes, or verifier outputs.

Does the script work only for this exact task instance, or is it parameterized?

It is hardcoded to this exact task instance. The task ID, user identity, order IDs, product IDs, item ID, and payment method are all fixed. That is intentional for M4 and should not be interpreted as a general crystallization engine.

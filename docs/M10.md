# M10 - Assistance Tier

Date: 2026-08-18

Status: complete. Stopped for review. M3 remains quota-blocked/partial and was not resumed.

## 1. Technical Summary

M10 tested the assistance tier on a flaky, unpromoted Retail cluster where promotion is not safe: compound pending-order modification tasks `41`, `71`, `78`, and `97`. The assistance layer kept Sonnet as the decision-maker. It supplied advisory plan scaffolding plus compact, pre-resolved read-only context derived from saved passing traces, but it did not pre-execute writes, did not use a safety gate, and did not use deterministic write scripts.

Measured result against the same three M3 partial seeds (`626729`, `373753`, `361454`):

| Metric | Raw agent, M3 partial | Assisted agent, M10 | Change |
| --- | ---: | ---: | ---: |
| Runs | 12 | 12 | 0 |
| DB passes | 9/12 | 10/12 | +1 pass |
| Pass rate | 75.0000% | 83.3333% | +8.3333 pp |
| Cached benchmark cost | $1.939581 | $1.786394 | -7.8979% |
| Cached agent cost | $1.613832 | $1.461164 | -9.4599% |
| Total tokens | 1,171,051 | 1,374,350 | +17.3604% |
| Agent tokens | 1,079,048 | 1,283,856 | +18.9804% |
| Agent LLM calls | 137 | 125 | -8.7591% |
| In-trajectory read tool calls | 69 | 44 | -36.2319% |

The assistance tier produced a modest cached-dollar reduction, mostly by cutting read-tool turns, but it did not reduce token count. The added assistance packet increased prompt tokens; prompt caching made part of that cheaper, so cost fell while total tokens rose.

Accuracy was not cleanly harmless. Aggregate same-seed accuracy improved from 9/12 to 10/12, and held-out tasks improved from 3/6 to 4/6, but two specific raw-pass cases regressed under assistance. This is the key M10 caveat: assistance did not appear to railroad the agent into a frozen path, but it can still perturb borderline decisions.

## 2. Target And Baseline

Target family:

```text
compound_pending_order_modification
```

Tasks:

| Role | Task IDs | Reason |
| --- | --- | --- |
| Derivation evidence | `78`, `97` | Passing traces showed the common address-plus-item modification shape, but with different passing write order. |
| Held-out measurement | `41`, `71` | Related compound tasks not used as the primary derivation shape; both are flaky in M3 partial. |
| Bias test | `71` | The user initially asks for address plus item changes, then changes payment choice and narrows item modification to only the backpack. |

Why this family is unpromoted: M3 partial classified `41`, `71`, `78`, and `97` as flaky-looking or unpromoted. Tasks `41` and `71` already had DB failures. Tasks `78` and `97` passed so far, but via multiple passing write skeletons. There is no single stable family write path safe enough for Type 1 promotion.

Historical M2 single-trial baseline for these four tasks was 4/4 pass at $0.751677 total cached cost, $0.187919 per task. For the main comparison, I used the M3 partial raw runs at the exact same three seeds as M10 because that gives a matched 12-run denominator without re-spending on raw baseline calls.

## 3. Assistance Layer

The assistance layer had two parts.

Plan scaffolding, derived from passing traces of tasks `78` and `97`:

```text
Identify the customer, inspect relevant orders, inspect product variants only when an item change is requested, explain proposed changes, ask for explicit yes/no confirmation, then make only the writes supported by the current conversation and policy. Deviate whenever the user changes their mind, asks for extra action, omits confirmation, or read context contradicts the usual path.
```

Pre-resolved read context, derived per task from read calls that appeared in prior passing traces for that task:

| Task | Prefetched read-only calls per run |
| --- | ---: |
| `41` | 5 |
| `71` | 8 |
| `78` | 5 |
| `97` | 5 |

The prefetch allowlist was limited to read tools: `find_user_id_by_email`, `find_user_id_by_name_zip`, `get_user_details`, `get_order_details`, `get_product_details`, `get_item_details`, and `list_all_product_types`. The harness asserts that no prefetch call is a write tool.

The agent still had access to all normal retail tools and could ignore the packet, repeat reads, add reads, ask questions, or choose any write sequence. No write arguments were forced.

## 5. Bias Test

The scaffold did not behave like a hard rail, but the result is not a clean pass.

Evidence against railroading:

- Task `78` needed an extra cancellation beyond the core address/item scaffold. The assisted agent performed the cancellation in all 3/3 runs and passed.
- Task `71` needed the item-change branch narrowed to the backpack only after the user changed their mind. The assisted agent did not modify the desk lamp in any run.

Evidence of remaining risk:

- Task `71` passed only 2/3 assisted runs, same as raw.
- In the failed assisted `71` run, the agent followed the user's final wording and changed only the backpack, leaving the address unchanged. The DB verifier expected the address change, so this failed programmatically. This looks more like user-simulator/evaluator tension than frozen-scaffold bias, but it is still an assisted-agent failure.
- There were two same-seed regressions overall: `41` trial 1 and `71` trial 0.

Conclusion: assistance did not blindly follow a frozen path off a cliff, but M10 does not prove assistance is harmless. It needs a larger, family-specific regression set before being treated as deployable.

## 6. Cost And Token Mechanics

The main savings came from fewer read-discovery loops:

| Tool-call metric | Raw | Assisted | Change |
| --- | ---: | ---: | ---: |
| In-trajectory read calls | 69 | 44 | -36.2319% |
| In-trajectory write calls | 28 | 31 | +10.7143% |
| In-trajectory read+write calls | 97 | 75 | -22.6804% |
| Agent LLM calls | 137 | 125 | -8.7591% |

Token/cost split:

| Token/cost field | Raw | Assisted | Change |
| --- | ---: | ---: | ---: |
| Non-cached input tokens | 456,344 | 339,345 | -25.6383% |
| Cache creation input tokens | 0 | 31,994 | +31,994 |
| Cache read input tokens | 690,480 | 979,373 | +41.8380% |
| Completion tokens | 24,227 | 23,638 | -2.4312% |
| Total tokens | 1,171,051 | 1,374,350 | +17.3604% |
| Cached benchmark cost | $1.939581 | $1.786394 | -7.8979% |

So the M10 answer is not "we reduced tokens." We reduced cached dollars and tool-turn re-derivation, while total token volume went up because the read-only assistance packet was inserted into the prompt. This is smaller and messier than Type 1 promotion, but it works without a safety gate because the agent still decides every write.

## 7. Safety Sanity

| Check | Result |
| --- | --- |
| Any writes pre-executed by assistance? | No. Prefetch write-call count was 0. |
| Were all prefetch calls read-only? | Yes. The harness allowlisted read tools only. |
| Did the agent make every write decision itself? | Yes. Every write in the trajectory came from the Sonnet agent. |
| Deterministic write script used? | No. |
| Promotion gate used? | No. |
| Model calls made by assistance prefetch? | 0. |

Model calls for measurement were still required because the agent and user simulator were Sonnet. The 12 assisted simulations used 203 total LLM calls: 125 assistant calls and 78 user-simulator calls. The quota probe used one additional direct Sonnet call with 10 input tokens and 2 output tokens; its cost is ESTIMATED at $0.000060 using the same Sonnet on-demand rates.

## 8. What Broke Or Surprised Me

The biggest surprise is that the token metric moved the wrong way. Prompt assistance reduced tool discovery and cached-dollar cost, but not total tokens. For a production assistance tier, the packet probably needs to be more compact or delivered through a cheaper memory/cache path.

The second surprise is the two regressions. They do not look like a simple "scaffold forced the wrong write" failure. They look like the assistance altered a borderline conversation enough that the agent made a different judgment. That matters: even suggestive context can perturb behavior.

Task `71` exposed a benchmark ambiguity. The simulated user can say to leave the shipping address unchanged, but the DB verifier expects the address change. The agent that follows the user's latest wording fails. That is a real limitation of using this task as a clean bias test.
